# HillGPX architecture

## Overview

HillGPX is a static web app. All venue and route data is committed JSON or GPX; community contributions (routes, photos, reviews, reports) and accounts go through Supabase. Deployment is Cloudflare Pages, with a GitHub Pages backup.

## Data contracts

All coordinates are `[lng, lat]` or `[lng, lat, elevation]` unless otherwise noted. Elevations are in metres. Distances are in metres.

### Venue (`src/types.ts`)

```ts
interface Venue {
  slug: string;
  name: string;
  type: VenueType;
  lat: number;
  lng: number;
  summitM?: number | null;
  gainM: number | null;
  elevationSource: ElevationSource;
  routeSlugs: string[];
  // optional fields omitted when null in generated output
}
```

Rules:

- `slug` is kebab-case, unique, stable. It links venues to routes.
- A venue with both `summitM` and `gainM` missing is dropped at build time.
- `elevationSource` must be one of `estimated | dem | community | verified`.
- `routeSlugs` is populated by `build_data.py` based on route proximity.

### Route (`src/types.ts`)

```ts
interface Route {
  slug: string;
  name: string;
  venueSlugs: string[];
  distanceM: number;
  gainM: number;
  lossM: number;
  loop: boolean;
  surface?: RouteSurface;
  difficulty?: RouteDifficulty;
  coordinates: RoutePoint[];
  source: 'curated' | 'community' | 'local';
  contributor?: string;
  description?: string;
}
```

Rules:

- `coordinates` are `[lng, lat, elevationM]`, simplified by Douglas-Peucker.
- `gainM` and `lossM` are computed with a 2 m noise threshold and a 5-point smoothing window.
- `loop` is true when the first and last points are within 100 m.
- Optional sidecar JSON may override auto-detected `surface`, `difficulty`, `description`, `contributor`, or venue links.

### Terrain model (`public/data/dem/sg-dem.json`)

```ts
interface DemHeader {
  west: number;
  south: number;
  east: number;
  north: number;
  width: number;
  height: number;
  noData: number;
  attribution: string;
}
```

The sibling `.bin` file is a row-major `Int16Array` of size `width * height`. Values are metres above sea level; `noData` marks missing samples.

## Build flow

1. Curated venues load first from `data/venues/hills.json`.
2. OSM peaks load from `data/venues/peaks.json`; peaks within 250 m of an existing venue are dropped as duplicates.
3. HDB blocks load from `data/venues/hdb-blocks.json`.
4. Photos attach by matching `data/photos.json` to venue slugs.
5. Routes parse from `data/routes/*.gpx`, compute distance/gain/loss, link nearby venues, simplify geometry, and write to `public/data/routes.json`.
6. The tallest 3% of each venue type are marked `notable`.
7. Null optional fields are omitted from generated JSON to keep payload small.

## Browser storage

- Favourites: `localStorage` key owned by `src/lib/venues.ts`.
- Saved local routes: `localStorage` key owned by `src/lib/localRoutes.ts`.
- Auth session: Supabase Auth's own localStorage key (`sb-<project-ref>-auth-token`), owned by `src/lib/auth.ts` through the shared client in `src/lib/api.ts` — the JWT auto-refreshes and rides on community calls, which is how `routes.user_id` gets stamped. The public username and avatar live in the `profiles` table (`supabase/migrations/20261022000000_accounts.sql`); avatars are 256 px JPEGs in the public `avatars` bucket.

Neither is considered authoritative for the public dataset. To publish a route, add the GPX to `data/routes/` and rebuild.

## User flows

### Find a place to train

1. The landing page shows three representative places per geographic or training category instead of an exhaustive wall of cards.
2. The user opens a place (in a new tab) or follows a row's title or its end-of-row *See all* card to frame that country or region on the map.
3. Map pills distinguish the venue types present in the dataset with visible glyphs; route pills show distance. The current generated data contains hills and HDB blocks, while the schema is ready for stairs, parks, carparks, and bridges as those datasets are curated.
4. Selecting a pill opens a concise summary. Opening the detail page reveals access notes, linked routes, photos, attribution, nearby venues, and the location map.
5. The primary next actions are **Show on map**, **Download GPX** when available, save, share, or report incorrect data.

### Find and use a route

1. The user switches to **Routes** from the landing page or map category bar.
2. Route cards and map pills expose distance and EG before selection; routes without source or terrain elevation say that elevation is unavailable instead of claiming zero EG.
3. Selecting a route frames its complete line and shows an elevation profile when elevation data exists.
4. The user downloads the GPX, or imports their own GPX to compare its profile and nearby venues locally.

### Contribute data

1. A user can submit a place, photo, rating, or route from the contribution actions.
2. Local ratings/photos remain in browser storage until a backend is configured.
3. Publishable routes enter through `scripts/import_gpx.py` or a reviewed GPX contribution, retain source/licence provenance, and are rebuilt into the static dataset.
4. OpenStreetMap route relations are the preferred scalable source because they are public, attributable, and reproducible. Official export APIs and author-provided files are also accepted. Login bypasses, private activities, and files without redistribution permission are not imported.

## Deployment

Cloudflare Pages' git integration builds and serves `dist/` at hillgpx.com on every push to `main` (`npm run build`, no server). `.github/workflows/deploy.yml` runs on the same push — `npm ci`, `npm run typecheck`, `npm run build` with `VITE_BASE=/HillGPX/` — and publishes `dist/` to GitHub Pages as a backup copy whose canonical links point at hillgpx.com. No Python, no credentials, no runtime server on either path.

### Repairing account setup (2026-10-24)

The public production API returned PostgreSQL `42703: column routes.user_id
does not exist` for the My uploads query. The profiles endpoint also returned
404. Creating `private.stamp_route_owner()` alone does not create the missing
columns, table, or trigger: PL/pgSQL can accept a function before those fields
are exercised. Account creation through Supabase Auth can therefore succeed
while account features remain unavailable.

Run `supabase/migrations/20261024000000_repair_accounts.sql` as one complete
query in the project's Supabase SQL Editor. It catches up the accounts and
contributor-sync migrations transactionally and can be rerun after partial
manual setup. It also creates profiles for existing Auth users without one,
preserving valid available metadata usernames and resolving collisions.
Existing routes with null `user_id` remain unowned; neither a matching name nor
an email is evidence of route ownership. Test with a new signed-in upload,
including Anonymous, then check My uploads and owner-only deletion. SQL changes
must be applied to Supabase separately from deploying frontend code.

Migration validation also found a syntax error in the original accounts SQL:
`email_for_username` was declared `language plpgsql` but its body was a bare
SELECT without BEGIN/END. The bootstrap declaration now uses `language sql`;
the repair and security migrations remove that email-lookup function entirely.
The repair also avoids truncating
provider-generated usernames to three characters with `rpad`, and preserves
uppercase letters before normalizing email-derived handles to lowercase.


### Account security hardening (2026-10-24)

`20261024010000_account_security.sql` removes the public username-to-email
lookup. Password login, confirmation resend and reset now take an email
address; Google sign-in and public usernames are unchanged. The all-in-one
`20261024000000_repair_accounts.sql` includes the same hardening, so new or
partially installed projects need only run that repair. Already repaired
projects can run the smaller security migration. Deploy the frontend changes
alongside it; older frontends can still log in using an email address.

Privileged deletion RPCs explicitly revoke PUBLIC/anon EXECUTE before granting
authenticated users access. Trigger functions also revoke client execution.
Ownership checks remain inside the deletion RPCs; merely being signed in does
not grant access to someone else's route. Existing storage RLS helper grants
are retained.

Download counters accept only public approved community routes or the six
committed slugs in `private.curated_route_slugs`; future committed routes need
an allowlist migration. Counting is best effort: unknown caller IPs are not
counted; a repeated route from the same salted IP within ten minutes is ignored;
quotas are 30/hour, 200/day per connection and 10,000/day overall, independently
of upload quotas. A transaction advisory lock prevents concurrent calls racing
the quota check. This bounds counter/log writes; it does not prevent traffic
from reaching the API. Files remain downloadable even when tracking is skipped.


To rerun the isolated SQL regression suite without adding a production dependency:

```bash
npm install --prefix /tmp/hillgpx-sql-tests --no-package-lock --no-audit --no-fund @electric-sql/pglite@0.5.11
HILLGPX_PGLITE_MODULE=/tmp/hillgpx-sql-tests/node_modules/@electric-sql/pglite/dist/index.js node scripts/test_account_migrations.mjs
```

The suite uses an in-memory PostgreSQL engine with stand-ins for Supabase Auth,
storage tables and crypto helpers. It applies the actual migrations and tests
missing, partial and already-installed accounts, reruns, profile backfill,
ownership, denied anonymous deletion, removal of email lookup, known-route
counting, repeat suppression and hourly/daily/global quotas. It never connects
to the live project. Full Supabase integration (including gateway-supplied IP
headers and physical storage deletion) still needs a staging project check.
